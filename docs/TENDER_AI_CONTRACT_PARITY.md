# Tender AI contract parity (GHM validator <-> ZAID Tender AI schemas)

GHM has no schema library, so the Gateway validators in `src/tender/` are hand-written. They are the
**authoritative** validators (owner decisions Q8-Q10); the Tender AI Zod schemas are additional only.
To stop the two drifting silently, parity is a **tested requirement**, not a convention.

## Mechanism (the repositories cannot import each other)

1. **Source of truth for the fixtures:** `zaidhqdev-sys/zaid-tenderai`, file
   `contract-fixtures/tracking-v1.json`, produced by `src/domain/tender/contract-fixtures.test.ts`.
   Every case's expected outcome (`tenderAiValid`) is **computed by running the real Zod schemas**, never typed
   by hand. That test also fails if the committed file differs from what the current schemas produce.
2. **Regenerate (Tender AI repo):** `UPDATE_CONTRACT_FIXTURES=1 npx vitest run src/domain/tender/contract-fixtures.test.ts`
3. **Copy byte-for-byte into GHM:** `src/tender/fixtures/tracking-v1.json` (do not edit it here).
4. **Pin:** update `PINNED.sha256` and `PINNED.tenderAiCommit` in `src/tender/tracking-contract-parity.test.ts`.
   The test fails if the copy's SHA-256 differs from the pin, and fails if any case is judged differently by the
   GHM validator.

Current pin: `tracking-v1.json` SHA-256 `55f34bc13a69a837a6963a6f310819a0e954a757749965619ebec617cf2e44e1`,
Tender AI commit `ac2c70ac411ec09c4a70c741ea619e833d5e547a` (branch `feat/tender-web-app`).

## What the tracking fixtures cover

36 create cases, 16 update cases, 10 path-id cases: boundaries (300/301, 120/121, 200/201, 500/501), trimming,
null clearing, unknown keys, actor/business injection, non-object bodies, `http`/`ftp`/`javascript` URLs, URL
credentials, whitespace in URLs, malformed or impossible instants, and path ids with leading zeros or signs.

## Reviewed differences (documented in the fixture as `ghmDiffers`)

* `stage: "archived"` on **update**: Tender AI's schema accepts it; GHM refuses it, because archiving is a
  separate owner/administrator operation with its own audit event type. Tender AI must call the archive route.

A first parity run found one real gap (whitespace inside a source URL accepted by Tender AI, refused by GHM and
the SQL CHECK). It was fixed on the Tender AI side so the two agree.

## Version-2 saved-summary fixtures (`summary-v2.json`, batch 3)

Same four steps. Source: `contract-fixtures/summary-v2.json` in Tender AI, generated by
`src/domain/tender/contract-fixtures-summary.test.ts` (`UPDATE_CONTRACT_FIXTURES=1 npx vitest run
src/domain/tender/contract-fixtures-summary.test.ts`). **Valid bodies are produced by the real `projectForStorage`;
every expected outcome is computed by the real `validateCreateAnalysis` and `parseSavedSummary`** (value `ok`, or the
refusal reason `invalid` / `too_large` / `unsupported`). A drift guard fails if the committed file differs from the
current contract. GHM copies it to `src/tender/fixtures/summary-v2.json` and pins the SHA-256 and Tender AI commit in
`src/tender/analysis-contract-parity.test.ts`.

Current pin: SHA-256 `c9a87404506c234ddca067eeeb21217892eeb9e397a188f2e1b4beb7c38ea91f`, Tender AI commit
`8d7d62177f9d2fa27b458aa6e4fd8c80fd509ebf`.

* **90 write cases** (13 accepted, 73 `invalid`, 2 `unsupported`, 2 `too_large`) and **92 read cases** (every create
  body's `result` is also run through the read validator, plus read-only shapes).
* Categories: valid complete (6), valid incomplete (4), valid truncated (3, one also incomplete), invalid coverage (21),
  unsupported (2), oversized (3 plus one oversized-and-invalid), evidence integrity (18), truncation flags (4),
  envelope/authority (28: injected actor/business/role, raw document text, wrong version/source, bad hash, ...).
* The GHM validator (`src/tender/analysis-contract.ts`) agrees with Tender AI on **every** case, including the
  refusal reason. Mutation checks confirmed each coverage, evidence, truncation, unsupported, oversized and duplicate-id
  rule is actually exercised: removing any one of them fails the parity test.
* Every coverage fixture was checked to fail for the reason in its name; one that failed for an earlier reason was
  corrected (it is why the pin moved from `1ed3ed97...` to `c9a87404...`).

### Differences found and fixed on the Tender AI side (GHM stays authoritative)

* Tracking: whitespace inside a source URL (batch 2).
* Summaries: `validateCreateAnalysis` enforced only the 16 KiB request limit, not the 12 KiB projection limit, so it could
  accept a result that `parseSavedSummary` would refuse to read back. It now refuses with `too_large`.

No reviewed difference remains for summaries. Trimming is the only normalisation, exactly as the Zod schemas do it
(`model`, `promptVersion` and province names); nothing else is converted, defaulted or repaired.
