## Qualification state

Unit-level construction qualification remains separate from live database qualification.

The live GHM PostgreSQL connectivity and catalog gates have materially succeeded. The current database is PostgreSQL 18.6 in `ghm_db`, with the `public` application schema and five existing application tables: `files`, `password_reset_tokens`, `profiles`, `todos`, and `users`.

The authenticated application connection uses `ghm_app_user`. PostgreSQL reports the effective role as `ghm_db_user`, through the existing role configuration/membership. This is an observed construction-state fact, not an instruction to change roles yet.

The captured database contains no application views, materialized views, routines, or triggers. Existing RLS is enabled on `files`, `todos`, and `users`, and disabled on `profiles` and `password_reset_tokens`. Existing policies use `app.current_user_id` and `app.current_user_role` settings. Existing foreign keys from `files`, `password_reset_tokens`, `profiles`, and `todos` reference `users.id` with cascade deletion.

Current effective table privileges are broad and grantable through `ghm_db_user`, including `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER`. The effective database/schema authority is also broader than the intended long-term least-privilege runtime boundary. This remains the principal database qualification finding.

No role changes have been made. Do not remove the existing role relationship or legacy role until migration/admin authority and runtime application authority are deliberately separated and verified.

## Database reconciliation gate

The live PostgreSQL catalog was successfully captured after correcting the local Render hostname and enabling PostgreSQL TLS for the capture connection.

The resulting evidence is metadata-only. It does not capture application rows, passwords, reset tokens, connection strings, JWT secrets, service keys, or other credentials.

The catalog confirms that GHM currently has only a small legacy/infrastructure schema. It does **not** contain Connect or QuoteFlow product tables, which is a positive architectural result: GHM has not been populated by blindly copying Zaid Connect's Supabase schema.

### Catalog interpretation

- `users`, `profiles`, and `password_reset_tokens` are an existing identity foundation.
- `files` is existing storage metadata and remains compatible with the decision to use Supabase Storage temporarily as an available/free provider behind a provider-neutral GHM storage capability boundary.
- `todos` is legacy/demo state and is not a canonical ZAID business domain.
- Existing RLS policies are legacy database behavior and must not be copied blindly into the target authorization architecture.
- Disabled RLS on `profiles` and `password_reset_tokens` is a legacy finding, not a target security decision.
- Identity, storage metadata, and legacy tables must be reconciled before deciding what survives into canonical GHM migrations.

The catalog capture query has now been hardened to exclude PostgreSQL internal schemas such as `pg_toast`. The clean catalog evidence was captured and committed separately as the database evidence artifact.

### Current database gate

Connectivity discovery is complete. The active gate is now **schema reconciliation plus least-privilege role-boundary design**.

The canonical authority model has now been documented in `docs/architecture/DATABASE_AUTHORITY_MODEL.md`. It establishes four distinct authority classes:

1. schema ownership;
2. migration authority;
3. runtime application authority;
4. observation/diagnostics authority where actually required.

The key decision is that the runtime role must not own schemas or possess `CREATEDB`, `CREATEROLE`, arbitrary DDL, or blanket destructive/structural privileges. A GHM application `admin` is an application authorization role, not a PostgreSQL database administrator.

No database role mutation has been performed as part of this decision. The next gate is evidence-led privilege reconciliation against actual runtime SQL and migration SQL.

## Storage provider decision

Supabase Storage is currently being used as an available/free storage facility. This does **not** make Supabase the GHM backend authority and does **not** block GHM construction.

The required architecture is:

```text
Product → GHM storage boundary → current provider (Supabase Storage for now)

Future:

Product → GHM storage boundary → ZAID-owned storage
```

Do not spend construction effort removing a useful temporary provider merely because it is Supabase. The architectural requirement is provider-neutrality at the GHM boundary so the provider can be swapped later without product rewrites.
