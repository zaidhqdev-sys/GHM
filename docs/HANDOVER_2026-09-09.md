## Database qualification state

The live GHM PostgreSQL connectivity and catalog gates have materially succeeded. The current database is PostgreSQL 18.6 in `ghm_db`, with the `public` application schema and five existing application tables: `files`, `password_reset_tokens`, `profiles`, `todos`, and `users`.

The authenticated application connection uses `ghm_app_user`. PostgreSQL reports the effective role as `ghm_db_user`, through the existing role configuration/membership. This is an observed construction-state fact, not an instruction to change roles yet.

The captured database contains no application views, materialized views, routines, or triggers. Existing RLS is enabled on `files`, `todos`, and `users`, and disabled on `profiles` and `password_reset_tokens`. Existing policies use `app.current_user_id` and `app.current_user_role`. Existing foreign keys from `files`, `password_reset_tokens`, `profiles`, and `todos` reference `users.id` with cascade deletion.

Current effective table privileges are broad and grantable through `ghm_db_user`, including `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER`. The effective database/schema authority is also broader than the intended long-term least-privilege runtime boundary. This remains the principal database qualification finding.

No role changes have been made. Do not remove the existing role relationship or legacy role until dedicated runtime and migration authority can be introduced and positively/negatively qualified.

## Database reconciliation gate

Connectivity discovery is complete. The active database gate is **schema reconciliation plus least-privilege role-boundary design**.

The canonical authority model is documented in `docs/architecture/DATABASE_AUTHORITY_MODEL.md`. It establishes four distinct authority classes:

1. schema ownership;
2. migration authority;
3. runtime application authority;
4. observation/diagnostics authority where actually required.

The key decision is that the runtime role must not own schemas or possess `CREATEDB`, `CREATEROLE`, arbitrary DDL, or blanket destructive/structural privileges. A GHM application `admin` is an application authorization role, not a PostgreSQL database administrator.

No database role mutation has been performed. The existing construction path remains intact while the dedicated runtime/migration model is prepared.

- `supabase/migrations/` is the authoritative Connect schema-evolution source;
- `src/supabase/supabase_schema.sql` exists but is a legacy/consolidated schema artifact and is not the current production schema authority;
- the migration history has materially evolved beyond that consolidated artifact;

A concrete divergence was verified: the consolidated schema declares PostgreSQL ENUMs and early structures such as `catalogue_items`, `conversations`, and `quotes`, while the authoritative migrations use later text/CHECK-based contracts and domain-specific replacements such as `business_offerings`, `project_quotes`, support conversations, and generalized Opportunity structures.

This closes the ambiguity around which Connect schema source GHM must trust: **migration history first, generated types/contracts second, application usage third; never the stale consolidated schema as a direct migration blueprint.**

## Business Identity operation contract gate

Direct Connect source inspection reconciled the first capability's concrete operation boundary. Identity resolution loads the canonical Profile, loads active Business memberships, and derives active Business context and permissions from an eligible membership. A single membership can auto-resolve; multiple memberships require a valid selection; invalid or revoked selections fail closed; selecting a Business does not change the Account Role.

Business creation is a server-backed Business service operation accepting the authenticated owner Account and Business name; the service derives the slug and returns the public-safe Business projection. Client-side validation is not treated as authoritative.

The owner editor provides an explicit editable-field set while excluding ownership, verification, activation, derived counters, ratings, and other governed state from ordinary Business updates. Registration identity is treated separately from the public Business projection.

The new GHM contract is recorded in `docs/architecture/BUSINESS_IDENTITY_OPERATION_CONTRACT.md`.

Important design decision: the first GHM migration candidate is intentionally smaller than Connect's current `businesses` table. Directory metadata, commercial state, reviews, trust, marketplace, analytics, and storage implementation are not pulled into the first identity migration merely because they reference Business.

## Storage provider decision

Supabase Storage is currently being used as an available/free storage facility. This does **not** make Supabase the GHM backend authority and does **not** block GHM construction.

The required architecture is:

```text
Product → GHM storage boundary → current provider (Supabase Storage for now)

Future:

Product → GHM storage boundary → ZAID-owned storage
```

Do not spend construction effort removing a useful temporary provider merely because it is Supabase. The architectural requirement is provider-neutrality at the GHM boundary so the provider can be swapped later without product rewrites.
