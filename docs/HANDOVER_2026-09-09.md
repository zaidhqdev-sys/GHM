## PostgreSQL authority reconciliation

Read-only privilege and ownership inspection has now established that the current construction database authority model is broader than the intended runtime boundary.

Current role chain:

`ghm_app_user` inherits:

- `pg_read_all_stats`;
- `pg_signal_backend`;
- `ghm_db_user`.

`ghm_app_user` itself is not superuser, CREATEROLE, CREATEDB, replication, or BYPASSRLS. However, its inherited `ghm_db_user` membership exposes the broader owner role's effective database/object authority.

Current `ghm_db_user` state:

- LOGIN — true;
- INHERIT — true;
- SUPERUSER — false;
- CREATEROLE — true;
- CREATEDB — true;
- REPLICATION — false;
- BYPASSRLS — false.

Effective privilege checks for `ghm_app_user` returned true for:

- database CONNECT;
- database CREATE;
- database TEMP;
- public schema USAGE;
- public schema CREATE;
- SELECT/INSERT/UPDATE/DELETE/TRUNCATE on `account_identity`;
- SELECT/INSERT/UPDATE/DELETE/TRUNCATE on `ghm_schema_migrations`.

The table-grant inventory also shows `ghm_db_user` has broad SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER privileges across both the new Business Identity tables and the legacy application tables.

Ownership inspection confirms:

- database `ghm_db` owner = `ghm_db_user`;
- schema `public` owner = `ghm_db_user`;
- current application tables and identity sequences are owned by `ghm_db_user`.

The public schema ACL currently grants `ghm_db_user` `UC`, while PUBLIC retains `U`. Database ACL is null in the inspected output. PostgreSQL default ACL inspection also shows broad defaults associated with the bootstrap `postgres` grantor, including table privileges for `ghm_db_user`.

### Authority conclusion

The current `ghm_app_user -> ghm_db_user` chain is **not an acceptable target runtime authority model**.

The correct architectural direction is role separation, not an isolated privilege patch:

- `ghm_schema_owner` — NOLOGIN, owns database objects where ownership is required;
- `ghm_migrator` — controlled migration/DDL authority, not the application runtime identity;
- `ghm_runtime` — LOGIN runtime identity with only measured application DML/read and required sequence privileges;
- application runtime must not receive schema ownership, schema CREATE, CREATEDB, CREATEROLE, TRUNCATE, TRIGGER, arbitrary sequence mutation, or migration-ledger authority.

PostgreSQL role membership and inheritance behavior supports this separation; role attributes such as CREATEDB/CREATEROLE are not ordinary inherited object privileges, while membership can expose object privileges and can permit `SET ROLE` where membership grants allow it. The final design must therefore explicitly control membership, INHERIT/SET/ADMIN options, object ownership, and default privileges.

No PostgreSQL role, ownership, membership, or grant mutation has been performed as part of this reconciliation.
