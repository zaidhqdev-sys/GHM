## Business Identity SQL reconciliation

The first migration defines exactly three Business Identity tables:

- `account_identity`
- `business`
- `business_membership`

with identity-backed bigint IDs, explicit role/status checks, Business slug uniqueness, one active owner per Business, and the required foreign keys/indexes. fileciteturn51file0L2-L2

Repository reads match the first-slice projection:

- Account: `id, full_name, phone, avatar_ref, role, created_at, updated_at`;
- Business: `id, name, slug, verification_status, is_active, created_at, updated_at`;
- Membership: all first-slice membership identity/lifecycle/audit fields.

Membership listing is intentionally active-only in the repository because `businessContext.listMemberships` is defined as the active-membership context boundary. Explicit invalid/revoked selection remains a service-layer fail-closed test using a repository that can surface inactive state.

Business creation is atomic within the authorized transaction: it creates the Business and then the owner membership. The first-slice database schema contains the structural constraints required to prevent duplicate slugs and multiple active owners. fileciteturn50file0L2-L2

The repository's current Business update path is limited to `name` and `slug`, which are the only editable Business columns in the first migration. This resolves the previous documentation/type drift: later Connect profile fields require a separately reconciled migration and must not be implied by the first slice.

## Runtime privilege boundary

The runtime grant design is intentionally least-privilege and based on measured repository SQL. Runtime requires SELECT on the three tables, profile INSERT/UPDATE for the authenticated account path, Business INSERT for creation, Business UPDATE only for first-slice `name`, `slug`, and `updated_at`, membership INSERT for owner participation, and identity-sequence usage for generated IDs.

Runtime must not receive schema ownership, CREATE on the application schema, CREATEDB, CREATEROLE, TRUNCATE, TRIGGER, arbitrary sequence mutation, arbitrary function execution, or migration-ledger authority. No role mutation has been performed.

The existing `ghm_db_user` remains broader than the target boundary and is not being treated as the target runtime role.
