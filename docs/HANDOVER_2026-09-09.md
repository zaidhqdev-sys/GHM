## PostgreSQL authority reconciliation

Read-only privilege, role-membership, ownership, and default-ACL inspection has established that the current construction database authority model is substantially broader than the intended runtime boundary.

Current role chain:

`ghm_app_user` inherits:

- `ghm_db_user`;
- `pg_read_all_stats`;
- `pg_signal_backend`.

`ghm_app_user` itself is not superuser, CREATEROLE, CREATEDB, replication, or BYPASSRLS. However, its inherited `ghm_db_user` membership exposes the broader owner role's effective database/object authority.

Current `ghm_db_user` state:

- LOGIN — true;
- INHERIT — true;
- SUPERUSER — false;
- CREATEROLE — true;
- CREATEDB — true;
- REPLICATION — false;
- BYPASSRLS — false.

Effective role-membership checks for `ghm_app_user` against `ghm_db_user` returned:

- USAGE — true;
- SET — true;
- MEMBER — true.

This proves the current application identity can both inherit and explicitly `SET ROLE ghm_db_user`. That is a direct failure of the target runtime authority boundary.

Effective privilege checks for `ghm_app_user` returned true for:

- database CONNECT;
- database CREATE;
- database TEMP;
- public schema USAGE;
- public schema CREATE;
- SELECT/INSERT/UPDATE/DELETE/TRUNCATE on `account_identity`;
- SELECT/INSERT/UPDATE/DELETE/TRUNCATE on `ghm_schema_migrations`.

The table-grant inventory also shows `ghm_db_user` has broad SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER privileges across both the new Business Identity tables and the legacy application tables.

Ownership inspection confirms:

- database `ghm_db` owner = `ghm_db_user`;
- schema `public` owner = `ghm_db_user`;
- `account_identity`, `business`, `business_membership`, `ghm_schema_migrations` = `ghm_db_user`;
- `account_identity_id_seq`, `business_id_seq`, `business_membership_id_seq` = `ghm_db_user`.

The public schema ACL currently grants `ghm_db_user` `UC`, while PUBLIC retains `U`. Database ACL is null in the inspected output.

Sequence inspection confirms all three identity sequences currently give `ghm_app_user` effective USAGE, SELECT, and UPDATE through the inherited broad authority path. The target runtime should start at USAGE only; SELECT/UPDATE require empirical qualification and must not be granted merely because they are currently present.

### Default ACL evidence

Read-only inspection of `pg_default_acl` returned database-wide defaults associated with the bootstrap `postgres` creator role:

- schemas: `postgres=rwU/postgres,ghm_db_user=rwU/postgres`;
- types: `=U/postgres,postgres=U/postgres,ghm_db_user=U/postgres`;
- functions: `=X/postgres,postgres=X/postgres,ghm_db_user=X/postgres`;
- tables: `postgres=arwdDxtm/postgres,ghm_db_user=arwdDxtm/postgres`.

These are default ACLs for future objects created by the recorded grantor, not evidence that `ghm_db_user` created the existing Business Identity objects. They nevertheless establish another broad authority path that must be reconciled before final runtime qualification.

### Authority conclusion

The current `ghm_app_user -> ghm_db_user` chain is **not an acceptable target runtime authority model**.

The correct architectural direction is role separation, not an isolated privilege patch:

- `ghm_schema_owner` — NOLOGIN, owns database objects where ownership is required;
- `ghm_migrator` — controlled migration/DDL authority, not the application runtime identity;
- `ghm_runtime` — LOGIN runtime identity with only measured application DML/read and required sequence privileges;
- application runtime must not receive schema ownership, schema CREATE, CREATEDB, CREATEROLE, TRUNCATE, TRIGGER, arbitrary sequence mutation, migration-ledger authority, or a SET ROLE path into owner/migrator authority.

No PostgreSQL role, ownership, membership, or grant mutation has been performed as part of this reconciliation.
