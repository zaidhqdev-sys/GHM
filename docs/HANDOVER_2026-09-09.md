## PostgreSQL authority reconciliation

Read-only privilege, role-membership, ownership, and default-ACL inspection established that the original construction database authority model was substantially broader than the intended runtime boundary.

The original role chain was:

`ghm_app_user` inherited:

- `ghm_db_user`;
- `pg_read_all_stats`;
- `pg_signal_backend`.

The original `ghm_db_user` state included LOGIN, CREATEROLE, CREATEDB, and broad object ownership/grants. The original `ghm_app_user -> ghm_db_user` membership had effective USAGE, SET, and MEMBER true, including explicit `SET ROLE ghm_db_user` capability.

Ownership before separation was:

- database `ghm_db` owner = `ghm_db_user`;
- schema `public` owner = `ghm_db_user`;
- first-slice GHM tables and identity sequences = `ghm_db_user`.

Default ACL inspection also showed broad defaults associated with bootstrap `postgres`. These were documented as future-object defaults for that creator role, not as evidence of authorship of existing Business Identity objects.

## Executed PostgreSQL role separation

Founder authorization for the exact construction-only PostgreSQL role/membership/ownership/grant/revoke plan was explicitly given on 2026-09-09.

### Target roles

Created and verified:

- `ghm_schema_owner` — NOLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION, NOBYPASSRLS;
- `ghm_migrator` — LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION, NOBYPASSRLS;
- `ghm_runtime` — LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOINHERIT, NOREPLICATION, NOBYPASSRLS.

No passwords are stored in GitHub or this handover.

### Migrator-to-owner path

Executed:

```sql
GRANT ghm_schema_owner TO ghm_migrator WITH INHERIT FALSE, SET TRUE;
```

A real login as `ghm_migrator` subsequently qualified the path:

- membership — true;
- SET ROLE capability — true;
- effective current role after `SET ROLE ghm_schema_owner` — `ghm_schema_owner`;
- session user remained `ghm_migrator`.

### GHM object ownership

The corrected ownership transfer succeeded for the four GHM-owned tables:

```sql
ALTER TABLE public.account_identity OWNER TO ghm_schema_owner;
ALTER TABLE public.business OWNER TO ghm_schema_owner;
ALTER TABLE public.business_membership OWNER TO ghm_schema_owner;
ALTER TABLE public.ghm_schema_migrations OWNER TO ghm_schema_owner;
```

PostgreSQL automatically transferred the three identity sequences to `ghm_schema_owner` because they are identity sequences owned by the corresponding tables.

The `public` schema was deliberately not transferred because unrelated legacy objects coexist there.

`ghm_db` database ownership was successfully transferred to `ghm_schema_owner`.

A temporary `CREATE` privilege on `public` was required for the ownership operation and was explicitly revoked immediately afterward. Final measured `ghm_schema_owner` CREATE privilege on `public` is false.

### Bootstrap membership blocker

An attempted cleanup of the original `ghm_db_user` memberships did not complete because those memberships were granted by bootstrap `postgres`, not by `ghm_db_user`.

The following memberships therefore remain and are explicitly recorded as unresolved:

```text
ghm_db_user -> ghm_schema_owner
ghm_db_user -> ghm_migrator
ghm_db_user -> ghm_runtime
```

They were measured with admin option true, inherit false, and set false. The temporary SET-capable membership used during ownership work was removed.

This cleanup cannot be performed by `ghm_db_user` because it is not the grantor. An independent bootstrap/provider-authority path is required. `ghm_db_user` must not be deleted as a substitute for this cleanup because it remains relevant to legacy-object recovery and provider bootstrap authority.
