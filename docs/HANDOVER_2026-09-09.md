# GHM Construction Handover — 2026-09-09

## Mission

GHM (GHM Core Engine) is being built as ZAID Technologies' own backend platform so Zaid Connect and QuoteFlow can eventually move away from managed backend dependency without production downtime.

## Non-negotiable production rule

Zaid Connect and QuoteFlow remain on Supabase until GHM is fully qualified. Do not change production environment variables, DNS, credentials, routing, or live product traffic during construction. Supabase remains the rollback path until controlled migration is complete.

- Mission Before Technology.

- One concept → one owner → one canonical source.
- GHM is not a copy of Supabase.
- Product repositories remain authoritative for their application contracts.
- Never invent product schema from assumptions.
- Infrastructure providers are replaceable implementations behind explicit GHM capability boundaries.

## Database reconciliation gate

The live GHM PostgreSQL catalog has not yet been successfully captured from the current environment. Therefore no business/product tables may be invented or migrated yet.

A repository script now exists at `scripts/capture-postgres-catalog.mjs` and is exposed as:

```text
npm run capture:postgres-catalog
```

It captures metadata only and does not read application rows, passwords, tokens, `DATABASE_URL` values, or secrets. It records PostgreSQL/server information, non-system schemas, tables, columns, constraints, foreign keys, indexes, sequences, views, materialized views, routines, triggers, RLS/policies, grants, and estimated row counts. The resulting evidence must be reviewed before committing because definitions/policies/routines can contain sensitive business logic.

Current development blocker: the configured Render PostgreSQL hostname has not resolved from the development environment. Render web-service deployment evidence proves GHM-Core is deployed, but does not by itself prove PostgreSQL reachability or establish the current database service/hostname. Do not claim live database qualification from the web-service deployment alone.

Required evidence before the first canonical GHM business migration:

- PostgreSQL server/version;
- schemas;
- tables and columns;
- types/nullability;
- primary and foreign keys;
- delete behavior;
- unique constraints and indexes;
- sequences/identity definitions;
- views/materialized views;
- functions/procedures;
- triggers;
- RLS state/policies;
- grants/privileges;
- safe row counts.

`ghm.db` is a tiny legacy SQLite artifact and is not schema authority.

## Storage provider decision

Supabase Storage is currently being used as an available/free storage facility. This does **not** make Supabase the GHM backend authority and does **not** block GHM construction.

The required architecture is:

```text
Product → GHM storage boundary → current provider (Supabase Storage for now)

Future:

Product → GHM storage boundary → ZAID-owned storage
```

Do not spend construction effort removing a useful temporary provider merely because it is Supabase. The architectural requirement is provider-neutrality at the GHM boundary so the provider can be swapped later without product rewrites.
