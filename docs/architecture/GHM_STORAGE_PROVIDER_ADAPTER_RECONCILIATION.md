# GHM Storage Provider Adapter Reconciliation

## Status
**CONSTRUCTION — RUNTIME CONFIGURATION BOUNDARY**

The provider-adapter implementation is reconciled onto the already-qualified PostgreSQL persistence boundary. This follow-on slice defines the runtime configuration contract without enabling production storage.

The qualified persistence branch remains the source of truth for ghm.storage_object. This slice does not modify the database, grant runtime table privileges, provision a bucket, or enable production credentials.

## Reconciled architecture

1. GHM storage service owns policy and caller/resource authorization.
2. PostgreSQL metadata is owned by the canonical storage persistence functions.
3. The runtime database role reaches storage metadata through those functions rather than direct table DML.
4. The provider adapter owns provider SDK interaction only.
5. Provider keys are generated by the GHM-owned key contract.
6. Provider state is verified before metadata becomes available.
7. Metadata enters deletion_pending before provider deletion and only becomes deleted after provider deletion succeeds.
8. Runtime provider configuration is owned by GHM deployment configuration, not business resources or product code.
9. The application selects the provider through a provider-neutral configuration contract; business logic does not receive bucket names, credentials, endpoints, or SDK clients.
10. Production storage configuration is fail-closed: provider identity, region, bucket, access key, and secret are required; custom endpoints must use HTTPS.
11. Upload grants are bounded to 900 seconds by default and never exceed 3600 seconds; download grants are caller-requested but bounded by the same 3600-second maximum.
12. Credentials are deployment secrets only and are never represented in source-controlled configuration.

## Runtime configuration contract

The repository defines:
- STORAGE_PROVIDER=s3
- STORAGE_ENDPOINT — optional S3-compatible endpoint; HTTPS only when supplied.
- STORAGE_REGION — required provider region.
- STORAGE_BUCKET — required container/bucket identity.
- STORAGE_ACCESS_KEY_ID — required deployment secret.
- STORAGE_SECRET_ACCESS_KEY — required deployment secret.
- STORAGE_FORCE_PATH_STYLE — optional boolean; defaults to true for a custom endpoint and false for native S3.
- STORAGE_UPLOAD_GRANT_TTL_SECONDS — optional, default 900, maximum 3600.
- STORAGE_DOWNLOAD_GRANT_MAX_TTL_SECONDS — optional, default 3600, maximum 3600.

The configuration loader returns a provider-neutral runtime configuration object. It does not construct an SDK client, contact a provider, provision infrastructure, or expose credentials to HTTP handlers.

## Environment separation

Local development/test values may be supplied through the developer environment. Production values must come from deployment secret/configuration management.

The repository does not authorize copying production credentials into .env.example, tests, fixtures, or committed source.

A custom S3-compatible endpoint is an infrastructure decision. Its presence does not change the GHM storage contract or grant business logic.

## Failure boundary

Configuration errors fail before storage provider construction. Provider outages remain provider errors; they must not cause metadata to be marked available.

A successful upload grant is not proof of object existence. The canonical completion flow must verify provider state before the metadata transition to available.

Deletion remains two-phase: deletion_pending is durable before provider deletion, and deleted is written only after provider deletion succeeds. A failed provider deletion therefore remains recoverable.

## Explicitly not authorized by this slice

- production bucket provisioning;
- production credentials;
- live uploads or downloads;
- provider health/reconciliation jobs;
- backup/recovery implementation;
- HTTP storage routes;
- changing PostgreSQL storage privileges;
- changing the canonical storage key contract.

## Next gate

This repository slice is configuration-boundary construction only. It is not a live-provider qualification.

Before production enablement, the next gate must wire this configuration into a single provider factory and perform a controlled live-provider qualification using deployment-managed test credentials and a dedicated non-production bucket/container. That qualification must verify real PUT/HEAD/DELETE behavior, signed upload/download behavior, checksum/metadata integrity, expiry, provider error mapping, and cleanup after failure.
