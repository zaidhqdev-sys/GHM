# GHM Business Identity Minimum Schema

Status: **construction schema qualified for the first slice; application repository qualification remains open.**

## Purpose

Define the smallest GHM-owned relational schema required by the reconciled Business Identity / Business Context operation contract. This is a capability schema, not a copy of Zaid Connect's Supabase schema.

## Canonical entities

### `account_identity`

Purpose: provider-neutral account/profile identity required by GHM identity resolution and self-service profile operations.

Columns:

- `id bigint generated by default as identity primary key`
- `full_name text null`
- `phone text null`
- `avatar_ref text null`
- `role text not null`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Initial role vocabulary is the existing GHM application vocabulary: `admin`, `customer`, `business`.

GHM owns this representation independently of any external authentication provider. Authentication credentials/tokens are outside this capability's relational schema.

### `business`

Purpose: stable Business identity and minimal lifecycle/public identity required by the first capability.

Columns:

- `id bigint generated by default as identity primary key`
- `name text not null`
- `slug text not null`
- `verification_status text not null default 'pending'`
- `is_active boolean not null default true`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Initial verification vocabulary is deliberately limited to the states required by the reconciled identity/public-read contract: `pending`, `approved`, `rejected`.

`slug` is unique and server-derived from Business name during creation. The service must handle slug collisions deterministically rather than delegating arbitrary caller-chosen identity semantics to the database.

### `business_membership`

Purpose: generalized Account-to-Business participation and context selection.

Columns:

- `id bigint generated by default as identity primary key`
- `business_id bigint not null references business(id) on delete cascade`
- `account_id bigint not null references account_identity(id) on delete cascade`
- `membership_role text not null`
- `membership_status text not null default 'active'`
- `created_by bigint null references account_identity(id) on delete set null`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Initial membership role vocabulary:

- `owner`
- `administrator`
- `member`

Initial membership status vocabulary:

- `active`
- `inactive`
- `revoked`

Required invariants:

1. `(business_id, account_id)` is unique.
2. A Business has at most one active owner.
3. Context resolution considers only `active` memberships.
4. Revoked/inactive memberships cannot authorize Business context.
5. Business deletion cascades membership deletion.
6. Account deletion cascades memberships; this is a GHM ownership decision for this first capability and must be reviewed before production cutover.

## Explicit non-goals

The first migration does not create or migrate:

- Connect directory metadata;
- commercial plans/subscriptions/payments;
- reviews/trust scores;
- opportunities/projects/quotes;
- notifications;
- support requests;
- business hours;
- capabilities/evidence;
- analytics/events;
- media/storage-provider records;
- Supabase Auth tables;
- password reset tokens;
- legacy `todos` or other GHM demo state.

Those domains require their own evidence-led capability gates.

## Field mapping decision

Connect `profiles` is not copied as a table. The GHM `account_identity` concept absorbs only fields required by the first GHM operation contract. Connect Business identity is likewise reduced to the minimum stable identity/lifecycle fields. Business membership retains the reconciled role/status semantics without copying Connect's full authorization machinery.

## Identifier strategy

GHM uses PostgreSQL identity-backed bigint identifiers for this first capability. External provider identifiers are not used as primary keys. This keeps GHM-owned identity independent of Supabase/Auth implementation details and provides efficient relational foreign keys.

## Timestamp strategy

`created_at` and `updated_at` are server-generated. The first migration does not introduce a generic update trigger merely for convenience. Repository/service writes must explicitly maintain `updated_at`; a trigger can be introduced later only if measured across multiple capabilities and documented as a shared GHM invariant.

## Authorization placement

Business authorization is a service-layer responsibility in the first implementation. Database constraints enforce structural invariants; they do not attempt to reproduce Connect's complete RLS/RPC authorization model.

This means the runtime SQL must be parameterized and scoped to authenticated identity/context, while PostgreSQL runtime grants remain least-privilege.

## Applied migration evidence

The schema defined here is now the canonical first-slice schema represented by repository migration `20260909150000_create_business_identity.sql`. The migration was applied to the construction database and recorded in `ghm_schema_migrations`; repeat/no-op and checksum integrity were qualified by the dedicated migration runner.

The live catalog also confirmed the expected tables, identity sequences, constraints, indexes, foreign keys, and absence of newly introduced views, routines, triggers, and RLS on these first-slice tables.

This schema qualification does **not** qualify the application repositories, authorization layer, transaction behavior, or production replacement.
