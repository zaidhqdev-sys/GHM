# GHM Quote Schema Contract

**Status:** CONSTRUCTION CONTRACT — SCHEMA DESIGN FROZEN

## 1. Purpose

Define the provider-neutral PostgreSQL schema for the QuoteFlow Quote capability.

The canonical relation is `ghm.quote`. It is distinct from `ghm.project_quote`.

No production migration or QuoteFlow cutover is authorized.

## 2. Ownership

QuoteFlow persistence is scoped to the active organization, with authenticated-user scope as the fallback when no organization is active.

GHM therefore models Quote ownership through the canonical GHM account/organization identity boundary. The Quote table must not use `business_id` as a substitute owner field and must not inherit Project Quote ownership semantics.

The exact organization-to-`ghm.account_identity` mapping remains governed by the existing GHM identity architecture.

## 3. Customer dependency

QuoteFlow requires a registered active Customer when creating a Quote. Customer is a distinct product concept and is not equivalent to `ghm.account_identity`.

The canonical GHM Customer resource is now constructed and runtime-qualified. `customer_id` therefore references `ghm.customer(id)` and Quote construction may proceed without inventing a second customer identity model.

## 4. Canonical Quote relation

`ghm.quote`

A row represents one sales quote owned by one authenticated account/organization and addressed to one registered Customer.

Canonical columns:

- `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `account_id bigint NOT NULL`
- `customer_id bigint NOT NULL`
- `customer_name text NOT NULL`
- `customer_phone text`
- `customer_email text`
- `description text NOT NULL`
- `amount numeric NOT NULL`
- `follow_up_date date NOT NULL`
- `status text NOT NULL DEFAULT 'active'`
- `reminder_id text`
- `reminder_date date`
- `notes text NOT NULL DEFAULT ''`
- `created_at timestamptz NOT NULL DEFAULT now()`
- `updated_at timestamptz NOT NULL DEFAULT now()`

`amount` deliberately uses unconstrained PostgreSQL `numeric`: QuoteFlow derives the amount directly from `quantity * unitPrice` and does not round the stored Quote subtotal. The separate invoice implementation rounds invoice calculations and must not be silently substituted here.

Quote line items are a child aggregate relation rather than JSON storage.

Canonical child relation:

`ghm.quote_line_item`

Columns:

- `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
- `quote_id bigint NOT NULL`
- `description text NOT NULL`
- `quantity numeric(14,4) NOT NULL`
- `unit_price numeric(14,2) NOT NULL`
- `catalog_item_id bigint NULL`
- `created_at timestamptz NOT NULL DEFAULT now()`

`catalog_item_id` is optional provenance only. No GHM catalogue Item capability is currently qualified, so the initial operation contract must not make catalogue Item existence a Quote prerequisite.

## 5. Customer snapshots

`customer_name`, `customer_phone`, and `customer_email` are Quote snapshots copied from the selected Customer at creation time.

The snapshot remains part of Quote history even if the Customer is subsequently archived or its contact details change.

The initial Quote operation contract does not authorize Customer reassignment or retroactive snapshot rewriting.

## 6. Line-item invariants

A Quote must contain at least one line item.

Each line item requires:

- trimmed non-empty description;
- finite quantity > 0;
- finite unit price > 0.

The Quote amount is derived from the submitted line-item subtotal at creation time and is stored without additional Quote-level rounding.

## 7. Description

The Quote description is a derived summary of the submitted line-item descriptions, joined with `, ` during creation.

It is persisted because it is part of the production Quote model and history surface.

The initial Quote create operation does not expose description as an independent free-form authority field.

## 8. Follow-up date

`follow_up_date` is required and represents the QuoteFlow `YYYY-MM-DD` follow-up date.

Reminder scheduling is not a database scheduler capability. `reminder_id` and `reminder_date` are metadata representing application scheduling state.

The GHM schema must not create notification-provider columns, device notification identifiers, or scheduling implementation state beyond these product-level fields.

## 9. Status

Canonical status vocabulary:

```text
active
won
lost
```

Initial status on creation:

`active`

No additional statuses are authorized.

## 10. Status mutation boundary

The production source exposes `setQuoteStatus(id, status)` for any differing target within the exact `active | won | lost` vocabulary. It does not establish a narrower transition graph.

Therefore the provider-neutral schema permits any differing status within the canonical vocabulary. Setting the same status is an idempotent no-op at the service behavior level.

Changing status clears existing reminder metadata. When the resulting status is `active`, an external application adapter may create replacement reminder metadata using the existing follow-up date.

The database must not itself schedule notifications.

## 11. Notes

Notes are independently mutable Quote state.

`notes` defaults to the empty string.

No separate Note resource is authorized by the current source.

## 12. Referential integrity

`account_id` must reference the canonical GHM account identity relation.

`customer_id` references `ghm.customer(id)`.

`quote_line_item.quote_id` must reference `ghm.quote(id)` with Quote-owned child lifecycle semantics.

Quote history must not be silently deleted by Customer archival.

The Customer resource currently has no runtime DELETE operation, so Quote history cannot be removed through Customer lifecycle operations.

## 13. Indexes

Required initial indexes:

- `(account_id, created_at DESC)` for owner history;
- `(account_id, status, follow_up_date)` for active/follow-up retrieval;
- `(customer_id, created_at DESC)` for Customer quote history;
- `(quote_id, id)` for deterministic line-item retrieval.

No speculative search indexes are authorized.

## 14. Runtime privilege direction

The runtime role must receive only the columns and relations required by the authorized Quote operations.

Runtime must have:

- schema USAGE;
- SELECT on Quote and Quote line items;
- INSERT on Quote client-supplied fields, excluding generated identity/timestamps/status defaults where possible;
- INSERT on Quote line-item client fields, excluding generated identity/timestamps;
- UPDATE only on fields authorized by the operation contract;
- sequence usage required for identity generation.

Runtime must have no DELETE privilege for Quote or Quote line items.

No blanket `GRANT ALL` is authorized.

Status UPDATE privilege, if required by the final repository implementation, is reserved for the governed status operation and must be qualified explicitly.

## 15. Provider-neutral boundary

The schema must not contain:

- Supabase UUIDs;
- `auth.uid()`;
- RLS policies;
- Supabase RPC identifiers;
- AsyncStorage keys;
- device notification implementation identifiers;
- QuoteFlow-specific authentication-provider identifiers.

GHM IDs are canonical.

## 16. Explicit exclusions

This schema does not include:

- Invoice;
- PDF generation;
- WhatsApp/calling behavior;
- notification scheduler implementation;
- Customer CRUD;
- catalogue Item CRUD;
- Quote customer reassignment;
- speculative Quote transitions;
- payment state;
- commercial subscription state;
- production data migration;
- production cutover.

## 17. Construction dependency gate

The Quote schema contract was dependency-gated on the Customer capability. That dependency is now satisfied:

1. canonical Customer resource constructed;
2. Customer account ownership boundary qualified;
3. Customer active/archived lifecycle qualified;
4. Customer durable historical references established;
5. final Quote foreign-keyed relations may now be constructed;
6. Quote repository/service operations may be implemented;
7. Quote runtime privileges and lifecycle behavior must then be qualified.

## 18. Qualification requirements

Before Quote is marked qualified, evidence must demonstrate:

1. account/organization ownership is enforced;
2. active Customer is required at creation;
3. inactive/archived Customer cannot be selected for new Quote creation;
4. customer snapshots are persisted correctly;
5. Quote line items are persisted atomically with Quote creation;
6. at least one valid line item is required;
7. invalid line-item quantity/price/description is rejected;
8. amount matches the production line-item subtotal semantics without Quote-level rounding;
9. follow-up date validation is correct;
10. exact status vocabulary is enforced;
11. all differing status operations within the exact vocabulary match source evidence;
12. notes mutation is isolated from unrelated fields;
13. reminder metadata is cleared/replaced according to status behavior without introducing scheduler infrastructure;
14. Customer archival does not erase Quote history;
15. unauthorized account access is denied;
16. runtime INSERT/UPDATE/SELECT privileges are least privilege;
17. runtime DELETE is denied;
18. concurrent mutations do not corrupt persisted Quote state;
19. repository/service tests pass;
20. live runtime qualification passes;
21. no existing qualified GHM capability regresses;
22. production safety remains intact.

## 19. Production safety

This contract authorizes construction only. Zaid Connect and QuoteFlow remain on their existing production backend. No production environment, credentials, routing, traffic, data, or Supabase schema may be changed by this contract.
