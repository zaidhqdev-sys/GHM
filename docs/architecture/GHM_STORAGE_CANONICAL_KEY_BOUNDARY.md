# GHM Storage Canonical Key Boundary

## Status

Construction boundary established; production storage remains unqualified.

## Verified Connect source

The existing Connect readiness evidence establishes that business logos historically use the Supabase Storage `media` bucket with the `logos/` object prefix.

GHM preserves the logical object namespace without preserving a Supabase runtime dependency.

## Canonical GHM key

Business-logo provider keys are:

`media/logos/<business-id>/<opaque-object-id>`

The business identifier is numeric and the object identifier is a UUID generated by GHM. User-controlled filenames, paths, extensions, and arbitrary path segments are not accepted as provider-key components.

## Ownership

- GHM owns object identity and provider-key construction.
- The storage service owns authorization, lifecycle and metadata semantics.
- The provider adapter owns only object-store operations and controlled access grants.
- The object provider remains replaceable.
- Supabase is historical source evidence only; it is not a runtime storage dependency.

## Security boundary

Provider keys are not accepted from callers. The service constructs them from validated internal identifiers.

The provider adapter never receives a user-controlled bucket/path selection. Provider-specific bucket configuration remains outside the service contract.

## Current object class

The first canonical class is `business_logo`.

Current policy remains JPEG/PNG/WebP, maximum 2 MiB, public visibility.

## Next boundary

The next implementation step is to connect `StorageMetadataStore` to the already-established PostgreSQL storage persistence functions. That wiring must preserve the existing narrow runtime table privilege boundary and must not grant direct table DML.
