### Enquiry architectural boundary

Enquiry is a customer-to-Business relationship and remains distinct from Project.

Canonical identity bindings:

```text
customer  -> ghm.account_identity.id
recipient -> ghm.business.id
```

Initial recipient authorization is deliberately limited to an active **owner** membership because the Connect source contract is owner-only. Do not broaden authorization to administrators or members without a new explicit contract.

### Initial governed operations

```text
enquiry.create
enquiry.readOwn
enquiry.readReceived
enquiry.updateStatus
```

Rules:

- authenticated customer may create an Enquiry;
- target Business must be eligible: approved and active;
- customer may not submit to their own Business;
- created status is `new`;
- customer identity comes from authenticated context;
- customer can read only own Enquiries;
- active Business owner can read received Enquiries for that Business;
- only the authorized Business owner can mutate lifecycle status;
- no delete operation;
- anonymous users have no Enquiry operations.

Lifecycle vocabulary remains:

```text
new -> contacted -> qualified -> quoted -> won | lost | archived
```

Source vocabulary is preserved:

```text
marketplace | directory | ai_quote | direct
```

Only the marketplace create path is initially eligible for implementation.

The first Enquiry slice must preserve the minimum source contract fields, including identity/business binding, customer snapshots, request title/description, city, budget range, urgency, source, status, and timestamps.

Do not automatically create a Project from an Enquiry.

Do not add notifications, realtime messaging, scoring, admin access, retention/anonymisation, anti-spam, payment, quoting, UI changes, provider migration, data migration, or Supabase RLS replication as part of this slice.
