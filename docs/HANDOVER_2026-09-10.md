# GHM Construction Handover — 2026-09-10

## Mission

GHM is being built as ZAID Technologies' own backend platform so Zaid Connect and QuoteFlow can eventually move away from managed backend dependency without production downtime.

## Continuity priority — Supabase dependency risk

On 2026-09-10 the Founder reported that Supabase has attempted to charge the account and that funds are not available. This creates a credible risk of service suspension and materially raises GHM's priority from strategic replacement work to business-continuity infrastructure.

This does **not** authorize an emergency production cutover. Supabase remains the current production backend and rollback/recovery provider until GHM has passed the governed qualification sequence. The immediate objective is to accelerate GHM qualification while preserving the ability to recover production safely.

Investigation findings:

- Zaid Connect and QuoteFlow production remain dependent on Supabase.
- No production environment variables, DNS, credentials, routing, traffic, or Supabase production data have been changed during this investigation.
- GHM's construction PostgreSQL database is reachable and the dedicated migration path is qualified.
- The immediate blocker for live application-runtime qualification is a usable `ghm_runtime` authentication credential, not evidence that the already-qualified runtime ACL boundary is wrong.
- Supabase production data must remain recoverable and must not be destructively modified because of billing/suspension risk.

## Investigation findings — PostgreSQL credentials and authority

The investigation reconciled the provider-managed credential surface with the SQL-created GHM role model.

### Provider-managed credentials

The Render PostgreSQL credential surface previously inspected exposes:

- `ghm_app_user` — Default
- `ghm_db_user`

It does not expose the SQL-created GHM roles as provider-managed credentials.

### SQL-created GHM roles

The construction database contains the separated roles:

- `ghm_schema_owner` — `NOLOGIN`, schema ownership authority;
- `ghm_migrator` — dedicated migration login;
- `ghm_runtime` — dedicated application runtime login.

These are PostgreSQL roles, not additional Render-managed credentials. Their credentials cannot be obtained merely by changing the username in a managed connection URL.

### Runtime credential finding

The existing `.env` `DATABASE_URL` authenticates through the legacy path as `ghm_app_user` and resolves to `ghm_db_user`. It is not a `ghm_runtime` connection.

A controlled test that changed only the username to `ghm_runtime` failed with PostgreSQL password authentication failure for `ghm_runtime`. Therefore the existing managed password cannot be assumed to be the password for the SQL-created runtime role.

The Founder confirmed that no separate PostgreSQL bootstrap credential is currently available. The investigation therefore identifies missing runtime credential/bootstrap authority as the current blocker to live runtime qualification.

### Historical password-reset path

An earlier construction session contained a script intended to execute:

```sql
ALTER ROLE ghm_runtime PASSWORD <new-password>
```

through the legacy `DATABASE_URL` path. This is historical evidence only. It must **not** be treated as currently authorized until the present authority of `ghm_db_user` is independently verified. No password is recorded in the repository or handover.

### Authority separation finding

The previous role-separation investigation established that the old path was broader than the intended runtime boundary:

```text
ghm_app_user -> ghm_db_user
```

The target architecture remains:

```text
ghm_schema_owner  (NOLOGIN)
        ^
        | explicit migration SET ROLE path only
        |
ghm_migrator      (migration process only)
ghm_runtime       (application runtime only)
```

Bootstrap/provider authority is still required to clean up legacy memberships safely. No deletion of `ghm_db_user`, weakening of runtime boundaries, or assumption of unproven provider authority is authorized.

## Investigation findings — live Business Identity qualification harness

The first live Business Identity runtime qualification attempt produced several useful findings that were separated from actual database authority failures:

1. The harness initially inherited an unrelated `CORS_ORIGINS` requirement. It was corrected to isolate runtime qualification from that application configuration.
2. The construction PostgreSQL endpoint requires TLS. The harness was corrected to use TLS with `rejectUnauthorized: false` for this construction qualification path.
3. Cleanup initially attempted direct `DELETE` operations as the migrator connection and correctly received `42501 permission denied`. This was a **harness cleanup-authority defect**, not a runtime ACL defect. The local harness was corrected to clean up in a transaction using `SET LOCAL ROLE ghm_schema_owner`.
4. After those corrections, the qualification reached the intended runtime identity check and refused to proceed because the supplied `DATABASE_URL` still resolved as `ghm_app_user`/`ghm_db_user` rather than `ghm_runtime`.
5. A direct `ghm_runtime` authentication test then failed with password authentication failure, confirming the remaining blocker is credential/bootstrap authority.

The corrected cleanup change is currently a local working-tree change and has not yet been committed/pushed. It must be preserved during the next code synchronization.
