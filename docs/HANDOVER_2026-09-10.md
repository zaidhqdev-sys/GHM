### 8. Read-only ad-hoc PostgreSQL audits — PowerShell-safe method

Avoid large `node -e` commands containing SQL, JavaScript template literals, backticks, or multiline quoting. PowerShell can transform those before Node receives them.

The reliable pattern is:

```powershell
@'
const { Pool } = require('pg');
require('dotenv').config();

const pool = new Pool({
  connectionString: process.env.GHM_RUNTIME_DATABASE_URL,
  ssl: { rejectUnauthorized: false },
});

(async () => {
  try {
    // READ-ONLY SQL ONLY
  } catch (error) {
    console.error(error);
    process.exitCode = 1;
  } finally {
    await pool.end();
  }
})();
'@ | Set-Content -Encoding UTF8 .\scripts\temporary-audit.cjs

node .\scripts\temporary-audit.cjs

Remove-Item .\scripts\temporary-audit.cjs
```

Important path rule: a temporary script under `scripts\` must require compiled repo modules with `../dist/...`, not `./dist/...`.

Important connection rule: `src/db/pool.ts` uses `config.databaseUrl`, which is `DATABASE_URL`. Therefore importing the canonical application pool is **not** a dedicated-runtime audit. For dedicated-runtime audits use the existing qualification harness or instantiate a temporary pool from `GHM_RUNTIME_DATABASE_URL` with the required TLS configuration.

## Terminal failures already diagnosed — do not repeat

### Failure A — PowerShell/Node inline SQL quoting

A large `node -e` command containing JavaScript template literals/backticks was mangled by PowerShell and reached Node as invalid escaped source, producing:

```text
Expected unicode escape
SyntaxError: Invalid or unexpected token
```

Resolution: use a temporary `.cjs` file with a PowerShell single-quoted here-string (`@' ... '@`).

### Failure B — wrong relative import from `scripts\`

A temporary `scripts\post-schema-audit.cjs` used:

```js
require('./dist/db/pool')
```

Node resolved that relative to `C:\GHM\scripts`, causing `Cannot find module './dist/db/pool'`.

Resolution: either use `../dist/...` from a script under `scripts\`, or better use the dedicated qualification harness / direct `pg` connection for the audit being performed.

### Failure C — canonical pool was the wrong connection for the dedicated-runtime audit

`src/db/pool.ts` reads:

```text
config.databaseUrl -> DATABASE_URL
```

The existing `DATABASE_URL` path is:

```text

```

It is not `GHM_RUNTIME_DATABASE_URL`.

Resolution: use `GHM_RUNTIME_DATABASE_URL` explicitly for dedicated-runtime qualification.

### Failure D — TLS

The construction PostgreSQL endpoint requires TLS for the dedicated runtime connection. The working temporary-audit configuration is:

```js

```

The repository's canonical pool applies TLS only when `NODE_ENV=production`; do not assume importing that pool selects `GHM_RUNTIME_DATABASE_URL`.

## PostgreSQL roles and authority

Target role separation:

```text
ghm_schema_owner (NOLOGIN)
        ^
        | explicit migration SET ROLE path only
        |
ghm_migrator (LOGIN, migration process only)
ghm_runtime  (LOGIN, application runtime only)
```

The old application path remains:

```text
ghm_app_user -> ghm_db_user
```

Measured authority facts:

- `ghm_runtime`: LOGIN, NOINHERIT, no elevated role attributes;
- `ghm_migrator`: LOGIN, NOINHERIT, explicit SET ROLE to `ghm_schema_owner`;
- `ghm_schema_owner`: NOLOGIN, NOINHERIT, owner of canonical GHM objects;
- `ghm_db_user`: legacy/provider-era role with `CREATEROLE=true` and `CREATEDB=true`;
- `postgres`: superuser, but customer does not possess its credentials.

The unwanted bootstrap memberships remain unresolved because they were granted by `postgres`:

```text
ghm_db_user -> ghm_schema_owner
ghm_db_user -> ghm_migrator
ghm_db_user -> ghm_runtime
```

Do not attempt to remove these memberships through an assumed authority path. Bootstrap/provider authority must be independently established before cleanup.

Do not delete `ghm_db_user` as a shortcut; it still owns legacy objects and remains relevant to recovery/bootstrap responsibilities.
